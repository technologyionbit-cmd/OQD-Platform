# Mock → Real Migration Strategy

## 1. Why this is tractable: the frontend was built for exactly this cutover

Every single mock datasource audited carries the same explicit, deliberate documentation: the repository interface and remote-datasource interface are already written to mirror what a real backend call looks like, and the *only* thing that should need to change is which concrete datasource a single Riverpod provider resolves to. Representative examples found directly in the code:

- `auth_data_source_provider.dart`: comment shows the exact intended future line, `AuthRemoteDataSourceImpl(ref.watch(dioProvider))`, in place of `AuthMockDataSource()`.
- `ai_mock_data_source.dart`: "Swapping in a real provider later only ever touches this file."
- `team_mock_data_source.dart`: "Temporary, isolated stand-in for the real backend."

This means the migration is not a redesign — it is a mechanical, per-feature swap, one provider override at a time, verified by the existing test suite (462 tests passing at freeze) plus new integration tests against the real API.

## 2. The general pattern, every feature follows it

```
MockDataSource  →  RemoteDataSourceImpl (dio-backed)  →  (Repository — unchanged)  →  (Provider/Controller — unchanged)  →  (UI — unchanged)
```

Concretely, per feature:
1. Implement `<Feature>RemoteDataSourceImpl` satisfying the **existing** `<Feature>RemoteDataSource` interface (already written for every feature, mirroring the mock 1:1) using `dio` (already configured with `AuthInterceptor`/`ApiErrorMapper`/`RedactingLoggingInterceptor` — this plumbing has been sitting ready and untested-against-a-real-backend since the frontend was frozen).
2. Flip the single provider override (e.g. `authRemoteDataSourceProvider`, `aiRemoteDataSourceProvider`) from the mock class to the new impl.
3. Run the feature's existing widget/unit tests against the real backend (via an integration-test target, not by mocking `dio` — the point is to prove the real contract matches) plus any new tests for behavior the mock couldn't exercise (real network errors, real latency, concurrent-booking races).
4. **No changes to `domain/` (entities, repository interfaces) or `presentation/` (controllers, screens) are expected** for any feature where the backend delivers the same contract already specified in its repository interface — deviations found during integration are contract bugs to fix on the backend side first, not automatic license to change the frontend.

## 4. Sequencing principle

Migrate in an order that lets each swapped feature be tested against a working backend before the next depends on it — see [16-backend-roadmap.md](16-backend-roadmap.md) for the exact phase ordering, which follows dependency order (auth → users/orgs/lawyers → contracts/documents → consultations → messaging/realtime → notifications → AI → billing), not audit order. Each phase's acceptance criteria explicitly include "the corresponding Flutter provider override flipped and the feature's existing test suite passing against the real API," so the frontend's already-frozen behavior is the regression baseline for every phase, not an afterthought at the end.

## 5. What must NOT happen during this migration

Per the explicit freeze: no `lib/` UI/UX changes beyond the narrowly-scoped, additive contract changes enumerated in §3 above (which are necessary because the mock's contract was in some cases incomplete relative to a real backend — e.g. contract signing, billing's missing repository layer — not because the UI itself is being redesigned). Any change beyond flipping a datasource provider and the specific additive items listed above should be treated as new product scope requiring its own sign-off, not bundled into "backend integration."
