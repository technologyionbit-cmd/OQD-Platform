# AI — Conversations & Contract Analysis

## 1. Entities

See [01-domain-model.md](01-domain-model.md) §8: `AiConversation`, `AiMessage`, `ContractAnalysis`, `AnalysisClause`.

## 2. What the mock actually fakes (so the real integration replicates the right behavior, not just the right shape)

The frontend's `AiMockDataSource` is explicitly documented in its own comments as "NOT a real AI integration" and a deliberate, isolated stand-in — its class doc states the intent plainly: swapping in a real provider should only ever touch that one file. That intent is the design goal here too: `AiRepository`'s method set is kept unchanged, only the datasource implementation changes.

- **Chat**: keyword-matched canned replies (no LLM), 900ms simulated latency, no streaming — the entire assistant reply appears at once after a spinner. `sendMessage({text, conversationId?})` is the single endpoint; `conversationId: null` starts a new conversation.
- **Analysis**: always the same 4 hardcoded clauses regardless of input document, `overallRisk` hardcoded to `medium`, 2200ms simulated latency (explicitly chosen in-code to make the "Analyzing..." loading state read as real work). Fully synchronous — no job/status concept exists at all.

## 3. Conversation scope — freeform, not per-contract

AI chat is a **general-purpose, freeform legal Q&A tab**, not scoped to a specific contract by default — it's the client's entire "AI" bottom-nav tab. Contract analysis is a **separate, distinct flow**: pick a document (from the vault, `sourceDocumentId`, or type a fresh title) → analyze → view a dedicated result screen. The one cross-link is a per-clause "Ask AI" button on the analysis result screen that opens a **brand-new freeform conversation** pre-seeded with a question — it does not attach the conversation to the analysis or contract by any foreign key. **This design is preserved as-is** — nothing in the audit suggests conversations should be contract-scoped by default; the backend just needs `AiConversation.userId` (missing today — see [01-domain-model.md](01-domain-model.md)) to make "freeform but private to me" actually true instead of the frontend's single shared global list.

## 4. Chat: streaming vs. request/response

No token-by-token streaming exists in the frontend today (full reply appears at once). **Approved decision** (see [16-backend-roadmap.md](16-backend-roadmap.md) §Phase 0 Product Decisions (Approved) item 6): **real AI chat supports streaming responses.** The backend uses Server-Sent Events or the same WebSocket connection from [07-messaging-realtime.md](07-messaging-realtime.md) to stream a real LLM's token output. This requires no change to `AiConversation`/`AiMessage`'s stored shape (the full assembled text is still what's persisted as one `AiMessage` row once the stream completes) — only the transport between "send" and "final message appears" changes, which is why the interface is designed for it now even though the **streaming implementation itself belongs to Phase 7** (when the real AI provider is integrated) rather than being built speculatively ahead of having a provider to stream from. The frozen UI's request/response pattern (§7 `POST /v1/ai/conversations/{id}/messages`) is written so it can be consumed either as a single awaited response or as a stream, so choosing streaming later at the transport layer does not require redesigning this endpoint's contract or the frontend's `AiRepository` interface shape.

## 5. Contract analysis: from synchronous mock to real async job

This is the one place in the whole AI feature where the mock's behavior (synchronous, instant result) **cannot** be replicated as-is with a real AI provider — real document analysis takes real time and the frontend's own 15s `dio` receive timeout ([05-api-design.md](05-api-design.md) §8) makes a long-held synchronous HTTP call actively unsafe to build against.

Design: `ContractAnalysis.status` (**new** enum: `pending, processing, completed, failed`) turns this into a genuine background job:

1. `POST /v1/ai/analyses {documentTitle, sourceDocumentId?}` → creates a `ContractAnalysis` row (`status = pending`), enqueues a job, returns `{id, status: pending}` immediately (well within timeout).
2. Worker picks up the job → `status = processing` → calls the real AI provider with the document content (extracted text — a real backend needs actual document text extraction, e.g. OCR/PDF-text-extraction for uploaded scans, since the frontend's own comment notes a freshly "uploaded" mock analysis target has `sourceDocumentId = null` precisely because there's no real file/OCR pipeline to attach one to) → on success, writes `AnalysisClause` rows + `overallRisk`/`summary`, sets `status = completed`, `completedAt`.
3. On failure (provider error/timeout), `status = failed`, `failureReason` set.
4. Client polls `GET /v1/ai/analyses/{id}` or — preferably, reusing the same WebSocket connection — receives an `ai_analysis.status_changed` push event, avoiding a polling loop. Once `completed`, a `Notification` (`aiAnalysisCompleted`) fires, exactly as the frontend already does today as a side effect of the (currently synchronous) call.
5. The frontend's `AiAnalysisSelectScreen`'s full-screen "Analyzing..." loading view continues to work unchanged during the `pending`/`processing` window — the UI already tolerates multi-second latency by design (it deliberately extended the mock's delay specifically so this state "reads as real work happening"); it just needs to keep polling/listening instead of awaiting one call, a controller-level change covered in [15-mock-to-real-migration.md](15-mock-to-real-migration.md).

## 6. Provider choice — not assumed

Per the task instruction, no specific AI provider is assumed here. The requirements this spec imposes on whichever provider is chosen: (a) supports a chat-completion API with conversation history, (b) supports long-context document input for contract analysis (contracts can be many pages), (c) ideally supports streaming responses for chat (§4). `ContractAnalysis.providerName` ([01-domain-model.md](01-domain-model.md) §8) records which provider/model produced a given result for audit/debugging and to allow provider migration without losing historical attribution.

## 7. Endpoint table

| Method & path | Auth | Purpose |
|---|---|---|
| GET /v1/ai/conversations | 🔒 | List current user's conversations, most-recent-first |
| GET /v1/ai/conversations/{id} | 🔒 | Full conversation incl. messages |
| POST /v1/ai/conversations/{id}/messages | 🔒 | Send (creates conversation if `id` omitted); streams response if client requests SSE/WS |
| DELETE /v1/ai/conversations/{id}/messages | 🔒 | Clear transcript (matches `clearConversation`) |
| GET /v1/ai/analyses | 🔒 | List current user's analyses |
| GET /v1/ai/analyses/{id} | 🔒 | Detail incl. clauses; poll-friendly while `pending/processing` |
| POST /v1/ai/analyses | 🔒 | Start analysis job (async, see §5) |
